# 项目协作与 Git 提交规则

> 本文件是本项目的**强制协作规范**，适用于所有协作者，以及在本项目中执行 Git 操作的所有 AI Agent。
> Agent 每次执行提交（commit）、推送（push）、拉取（pull）前，必须先阅读并遵守本文件。

---

## 0. 项目基本信息

| 项目 | 值 |
|------|-----|
| 远程仓库 | `https://github.com/zjr2110/lxw-game.git` |
| 主分支 | `main` |
| 协作方式 | 多人协作，功能分支 + Pull Request |
| 本地忽略文件 | 见仓库根目录 `.gitignore` |

---

## 1. 分支策略

1. **禁止直接向 `main` 分支提交业务代码。** 每个功能/修复都应新建独立分支。
2. 分支命名规范：

   | 类型 | 命名格式 | 示例 |
   |------|----------|------|
   | 新功能 | `feature/描述` | `feature/login-page` |
   | 缺陷修复 | `fix/描述` | `fix/score-calc` |
   | 文档 | `docs/描述` | `docs/api-guide` |
   | 重构 | `refactor/描述` | `refactor/render-loop` |
   | 杂项 | `chore/描述` | `chore/update-deps` |

3. **紧急小改动例外**：仅限单个文件、单行级别的修正（如错别字、依赖版本号），经确认后方可直接提交到 `main`。

---

## 2. Agent 提交前必须执行的检查清单

Agent 在提交前，必须**按顺序**完成以下动作，缺一不可：

1. `git status` —— 确认当前分支与待提交文件。
2. `git pull --rebase` —— 拉取最新代码（若处于功能分支且尚无远程跟踪，则 `git pull --rebase origin main`）。
3. `git diff`（或 `git diff --staged`）—— **审查所有将被提交的改动**，确认内容符合用户意图。
4. 确认待提交文件中**不包含**：
   - 密钥、Token、密码、`.env` 等敏感信息；
   - `.gitignore` 已声明的本地文件；
   - 依赖目录、构建产物、日志、缓存等非源码文件。
5. 确认改动**确实完成且可运行**，未完成的半成品不得提交。

> 若上述任一项不通过，Agent 必须**停止提交**，并向用户说明原因，等待指示。

---

## 3. 暂存（staging）规范

1. **优先显式指定文件**：`git add <文件1> <文件2>`，而非无脑全量添加。
2. 允许使用 `git add .` 的前提：已通过 `git status` 确认待添加列表中**只有本次改动涉及的文件**。
3. **禁止**使用 `git add -f` / `git add --force` 强制添加被忽略的文件。
4. **禁止**将临时调试文件、备份文件（如 `*.bak`、`*.tmp`、`*_old.*`）提交到仓库。

---

## 4. 提交信息（Commit Message）规范

采用 Conventional Commits 格式：

```
<type>: <简短描述>
```

**类型（type）取值：**

| type | 含义 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |
| `style` | 格式调整（不影响逻辑） |
| `refactor` | 重构（既不新增功能也不修 bug） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `chore` | 构建/依赖/工具等杂项 |

**要求：**

- 描述使用**中文**，简洁准确，说明「做了什么」及必要的「为什么」。
- 单次提交只做一件事，避免一个 commit 混入多个不相关的改动。
- 示例：
  ```
  feat: 新增游戏登录页面
  fix: 修复排行榜分数计算错误
  docs: 补充接口调用说明
  chore: 更新 .gitignore 忽略本地配置文件
  ```

---

## 5. 推送（Push）规范

1. 推送前必须已完成第 2 节检查清单。
2. 推送顺序：

   ```powershell
   git push
   ```
   若报 `rejected`（远程有新提交）：
   ```powershell
   git pull --rebase
   git push
   ```

3. **禁止**向 `main` 执行 `git push --force` 或 `git push -f`。
4. 若因 rebase 必须强推，**仅允许**对个人功能分支使用 `--force-with-lease`，且推送前须告知用户。

---

## 6. 禁止事项（红线）

以下操作**一律禁止**，除非用户明确书面要求：

1. ❌ `git push --force` / `--force-with-lease` 到 `main` 或他人分支；
2. ❌ `git reset --hard`、`git clean -fd`、`git checkout -- .` 等可能丢失未提交内容的破坏性命令；
3. ❌ 修改全局 Git 配置（`git config --global`）；
4. ❌ 提交任何密钥、Token、密码、证书文件；
5. ❌ 提交 `.gitignore` 中已忽略的文件；
6. ❌ 在未告知用户的情况下删除文件、回退提交或改写历史；
7. ❌ 在用户未要求时主动执行提交/推送（详见第 8 节）。

---

## 7. 冲突（Conflict）处理

1. 遇到冲突时，Agent **必须逐个文件分析冲突内容**，理解双方改动意图。
2. **不得**盲目选择 `--ours` 或 `--theirs` 一键解决。
3. 冲突解决后，运行 `git add <已解决文件>` 并 `git rebase --continue`（或 `git commit`）。
4. 若冲突涉及逻辑判断、业务语义且无法确定正确方案，**必须停止并询问用户**。
5. 若 rebase 过程中出现无法处理的状态，使用 `git rebase --abort` 回到安全状态后报告用户。

---

## 8. Agent 执行提交/推送的授权边界

1. **默认不主动提交**：Agent 完成代码修改后，应告知用户改了什么，**等待用户明确指令**后再提交。
2. 用户授权方式示例：「提交」「帮我提交」「commit 一下」「提交并推送」。
   - 「提交」= 仅 `commit`；
   - 「提交并推送」= `commit` + `push`。
3. 若用户授权中未提及推送，**只提交不推送**。
4. Agent 不得自行决定提交时机和提交信息风格，须遵循本规范第 4 节。

---

## 9. 环境注意事项（Windows / PowerShell 5）

1. 本项目开发环境为 **Windows + PowerShell 5**。
2. PowerShell 5 **不支持** `&&` 和 `||` 串联命令，需用 `;` 分隔，或分多条命令执行。
3. 路径包含空格时，必须使用双引号包裹，例如 `"d:\Trae code\work_space\Young Worldor"`。
4. 换行符统一：仓库以 LF 存储。`.bat` 文件保留 CRLF。新增文本文件请遵循仓库现有风格。
5. 若仓库根目录存在 `.gitattributes`，以其规则为准。

---

## 10. Agent 完成后的回报要求

Agent 每次提交/推送完成后，**必须**向用户报告以下信息，作为可核验的证据：

1. 当前分支名；
2. 本次提交的 commit hash（短 hash 即可）与提交信息；
3. 提交的文件清单；
4. 推送结果（成功 / 失败及原因）；
5. 若失败，给出具体错误信息与**可执行的**下一步方案。

> 禁止在未真正执行成功的情况下宣称「已提交/已推送」。

## 11. 队友首次克隆须知

```powershell
git clone https://github.com/zjr2110/lxw-game.git
```

克隆后请各自设置**本人身份**，不要共用同一账号：

```powershell
git config user.name "你的名字"
git config user.email "你的邮箱"
```

各自本地的忽略文件请自行维护，不提交到公共仓库。

---

*本规范如与用户当次明确指令冲突，以用户指令为准；用户指令执行完毕后，仍回归本规范。*
